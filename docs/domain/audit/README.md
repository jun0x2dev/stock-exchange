# audit

## 정의

로그인, 주문, 취소, 입금, 원장 정정의 성공과 실패 기록. 기록한 뒤 바뀌거나 지워졌는지 검사한다.

## 주요 상태/흐름

```
업무 트랜잭션 ─▶ audit_log + audit_pending ─(1초)─▶ audit_chain ─(1분)─▶ DB 밖 파일
```

- 성공은 업무 트랜잭션에서, 실패는 롤백돼도 남도록 별도 트랜잭션에서 저장한다.
- 로그인 실패는 입력한 아이디를 남기지 않는다. 아이디 칸에 비밀번호를 잘못 넣는 경우가 있다.
- 로그인한 사용자가 권한 없는 관리 기능을 시도하면 남긴다.
- 체인은 앞 칸의 해시와 로그 내용으로 HMAC-SHA256을 계산한다. 키가 DB에 없어 DB를 고칠 수 있는 사람도 다시 계산할 수 없다.
- 감사 담당자(AUDITOR)가 `GET /api/v1/admin/audit/verification`으로 전체를 다시 계산한다.

| 공격 (DB 관리자) | 드러나는 이유 |
|---|---|
| 내용 수정, 값을 옆 컬럼으로 이동 | HMAC이 다르다. 값마다 길이를 붙여 이어 붙이기로 속일 수 없다 |
| 로그 삭제, 체인까지 삭제 | 체인 번호가 비거나 앞 칸과 이어지지 않는다 |
| 뒤쪽을 통째로 삭제 | DB 밖 파일에 남긴 값이 체인에 없다 |
| 체인에 넣기 전에 대기 목록에서 빼기 | 1분 넘게 체인에 없는 로그로 드러난다 |

## 한계

- 체인에 들어가기 전(약 1초) 고친 로그와, 파일에 남기기 전(최대 1분) 뒤쪽을 통째로 지운 것은 찾지 못한다.
- 앱 서버까지 장악하면 키와 파일을 모두 바꿀 수 있다. 운영이라면 파일을 쓰기 전용 저장소에 둔다.
- 키를 바꾸면 이전 기록을 검증할 수 없다. 키 교체는 3단계의 남은 작업이다.
- CSRF·인증 실패처럼 보안 필터에서 막힌 요청은 남기지 않는다. 인증 없이 기록을 무한히 쌓을 수 있기 때문이다.
