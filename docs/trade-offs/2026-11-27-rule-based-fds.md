# 이상거래 탐지를 어디서, 어떻게 돌릴 것인가

## 선택지

1. 주문을 받을 때 검사해 막는다.
2. 엔진 결과를 받는 Kafka 소비자에서 실시간으로 상태를 쌓아 검사한다.
3. 주기적으로 DB의 최근 기록을 SQL로 훑는다.

## 선택

3번. 10초마다 최근 10분을 다시 보고, 같은 사건은 유일 제약으로 한 번만 경보한다. 별도 모듈(`exchange-fds`)로 나누지 않고 core 안에 둔다.

## 이유

- 스푸핑은 주문을 **취소한 뒤에야** 판단할 수 있다. 1번은 판단할 근거가 아직 없고, 정상 주문을 지연시킨다.
- 2번은 재시작할 때 상태를 다시 쌓아야 하고, 규칙을 바꾸면 소비자를 다시 만들어야 한다. 3번은 규칙이 SQL 하나라 기록 전체에 바로 다시 돌려 볼 수 있다.
- 매번 다시 보면 커밋 순서가 뒤바뀐 기록도 놓치지 않고, 중복은 DB가 막는다.
- 모듈 분리는 4단계 설계에 있지만, 지금은 규칙 하나라 프로세스를 늘릴 이유가 없다. 규칙이 늘어 core의 DB 부하가 문제가 되면 읽기 전용 복제본과 함께 나눈다.
- 감수한 점: 경보까지 최대 10초가 걸리고, 10분 넘게 꺼져 있던 구간은 놓친다.
