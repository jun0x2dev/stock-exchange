# 1단계에서 DB를 명령 큐로 쓰기

## 선택지

1. 커밋 후 메모리 큐에 주문을 넣고, 재시작할 때만 DB에서 미전달 주문을 다시 넣는다.
2. 커밋 후에는 종목에 신호만 보내고, 워커가 항상 DB에서 접수 대기 주문을 읽는다.

## 선택

2번.

## 이유

- 1번은 장애 복구 중에 큐에 남은 주문과 DB에서 다시 읽은 주문이 겹쳐, 이미 매칭한 주문 목록을 따로 관리해야 한다.
- 2번은 평소, 재시작, 저장 실패 복구가 모두 같은 코드를 탄다. 자주 실행되는 경로가 곧 복구 경로라 따로 썩지 않는다.
- 대기 작업이 종목 수를 넘지 않아 큐 크기 제한이 필요 없다.
- 감수한 점: 묶음마다 조회가 한 번 더 생긴다. 부분 인덱스로 대기 주문만 읽는다. 명령 순서는 DB 시각과 주문 ID로 정하므로, 시간 우선의 기준은 접수 시각이 아니라 엔진이 붙인 `engine_seq`다.
- 2단계에서 Kafka로 바꾸면 outbox의 명령 순번이 이 역할을 대신한다.
- 2026-11-25: 2단계에서 [Kafka와 Outbox](2026-11-25-engine-exactly-once.md)로 바꿔 이 방식은 더 이상 쓰지 않는다.
