# 주문 접수가 느린 원인 나누기

## 목적

[강제 종료 실험](2026-11-24-kill-under-load.md)에서 접수 지연이 목표(p99 100ms)를 크게 넘었다. 계좌 잠금과 커밋 동기화(디스크) 중 무엇이 원인인지 나눈다.

## 환경·방법

- i7-12700F, Windows 11, Docker Desktop(WSL2)의 PostgreSQL 17, 부하 생성기(k6)도 같은 PC. PC 사용에 지장이 없도록 백엔드는 힙 384MB·CPU 2개·낮은 우선순위, k6는 CPU 1개로 제한했다. 절대 처리량을 재는 실험이 아니다.
- 별도 DB에서 초당 5, 10, 20, 40건을 15초씩 보낸다(동시 요청 최대 24개, 종목 6개). 조건마다 1회만 쟀다.
- 조건: 계좌 3개 집중 / 30개 분산 × `synchronous_commit` on / off. **off는 원인을 나누기 위한 것이며, 커밋을 잃을 수 있어 실제로는 쓰지 않는다.**
- Docker 데이터는 **HDD**(SATA ST4000DM004)에 있다. 먼저 잰 디스크 동기화: `pg_test_fsync`의 `fdatasync` 22.6회/초(1회 44ms)
- 재현: `bench-accounts.sql` → `bench-deposit.mjs` → `order-rate.js` (이 폴더). 조건을 바꾼 뒤에는 기존 DB 연결을 끊어야 설정이 적용된다.

## 결과

접수 지연 p50 / p99 (ms)

| 조건 | 5건/초 | 10건/초 | 20건/초 | 40건/초 |
|---|---:|---:|---:|---:|
| A. 계좌 3, 동기화 on | 49 / 245 | 46 / 280 | 83 / 583 | 339 / 1,493 |
| B. 계좌 30, 동기화 on | 51 / 269 | 53 / 392 | 71 / 482 | 77 / 437 |
| C. 계좌 3, 동기화 off | 9 / 16 | 8 / 15 | 8 / 13 | 7 / 12 |
| D. 계좌 30, 동기화 off | 8 / 12 | 8 / 15 | 8 / 15 | 7 / 13 |

| 조건 | 접수~체결 p50 / p99 (ms) | 부하 종료 시 미처리 | 모두 처리까지 |
|---|---:|---:|---:|
| A | 4,158 / 21,152 | 386건 | 16초 |
| B | 262 / 5,432 | 92건 | 4초 |
| C | 10 / 26 | 0건 | 1초 이내 |
| D | 10 / 29 | 0건 | 1초 이내 |

- 모든 조건에서 불변식 위반은 0건이었다. 접수~체결은 체결 행을 쓴 시각까지이며 커밋 시간은 포함하지 않는다.
- A의 40건/초는 약 600건 중 528건만 접수됐다(동시 요청 한도에 걸림).

## 결론

- **주원인은 커밋마다 일어나는 디스크 동기화다.** 동기화를 끄면 계좌 수와 관계없이 p99가 16ms 이하다. 가장 낮은 5건/초에서도 p50이 동기화 1회 시간(44ms)과 비슷하다.
- **계좌 집중은 이를 키운다.** 같은 계좌의 커밋은 앞 커밋의 동기화를 기다리므로 줄을 선다. 40건/초에서 p99가 3배(437 → 1,493ms)였다.
- **매칭이 특히 밀린다.** 명령마다 한 번 커밋하므로 종목당 초당 약 22건을 넘을 수 없다. 디스크가 빨라지면 한계가 높아지지만 구조는 남는다.
- 한계: 조건별 1회, 15초씩이라 p99는 표본이 적다. DB 대기 이벤트 수집은 실패해 잠금 대기 시간을 직접 재지 못했다. 조건을 A→D 순서로 쟀다.

## 개선 후 비교

워커가 명령을 최대 20개씩 묶어 커밋하게 바꾸고([결정](../trade-offs/2026-11-24-batch-settlement.md)) A, B를 같은 방법으로 다시 쟀다. 동기화는 켠 상태다. Docker 데이터를 SSD로 옮기는 방법은 이 환경에서 쓸 수 없어 제외했다.

| 조건 | 지표 | 개선 전 | 개선 후 |
|---|---|---:|---:|
| A. 계좌 3 | 접수~체결 p50 / p99 (ms) | 4,158 / 21,152 | 1,151 / 6,996 |
| A. 계좌 3 | 부하 종료 시 미처리 | 386건 | 0건 |
| A. 계좌 3 | 접수 p99 (40건/초) | 1,493ms | 1,502ms |
| B. 계좌 30 | 접수~체결 p50 / p99 (ms) | 262 / 5,432 | 101 / 783 |
| B. 계좌 30 | 부하 종료 시 미처리 | 92건 | 0건 |
| B. 계좌 30 | 접수 p99 (40건/초) | 437ms | 484ms |

- **체결은 크게 빨라졌고 밀린 주문이 없어졌다.** 불변식 위반은 0건이었다.
- **접수 지연은 나아지지 않았다.** 접수는 주문마다 커밋해야 응답할 수 있어 묶을 수 없다. 5건/초에서도 p99가 277~288ms다.
- 재측정 직후 디스크 동기화는 1회 69ms로 처음(44ms)보다 느렸다. 전후 조건이 완전히 같지는 않다.
- 목표(접수 p99 100ms, 접수~체결 p99 300ms)는 **이 HDD 환경에서 달성하지 못했다.** 동기화 1회가 44~69ms라 접수 p99 100ms는 어렵다. 빠른 디스크에서 다시 재야 한다.
