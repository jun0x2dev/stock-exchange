# 부하 중 강제 종료

## 목적

주문을 받던 서버가 갑자기 죽어도 접수 응답을 보낸 주문이 남아 있는지, 재시작하면 밀린 주문과 취소가 처리되는지, 불변식이 유지되는지 확인한다.

## 환경·방법

- Windows 11 노트북, Docker Desktop(WSL2)의 PostgreSQL 17, 백엔드는 `bootRun` 단일 프로세스, 부하 생성기도 같은 PC
- 체험용 계좌 3개에서 8개씩 24개 동시 요청으로 6개 종목에 지정가 주문과 취소를 보낸다.
- 5~7초 뒤 `taskkill /f`로 프로세스를 종료하고, 종료 직후와 재시작 후에 대사 뷰 `invariant_violation`을 조회한다. 3회 반복한다.
- 재현: `EXCHANGE_DEMO_PASSWORD=... node docs/experiments/order-load.mjs http://localhost:8080 60 accepted.txt`

## 결과

| 회차 | 접수 응답 | DB에 없는 주문 | 종료 직후 미처리 주문 / 취소 | 종료 직후 위반 | 재시작 후 위반 | 재시작~모두 처리 |
|---|---:|---:|---:|---:|---:|---:|
| 1 | 195 | 0 | 168 / 3 | 0 | 0 | 19.7초 |
| 2 | 169 | 0 | 144 / 4 | 0 | 0 | 16.2초 |
| 3 | 242 | 0 | 206 / 8 | 0 | 0 | 17.9초 |

- 처리 시간에는 Gradle과 Spring Boot 기동이 포함된다. 정지된 종목은 없었다.
- 접수 지연은 p50 341~493ms, p99 966~1,712ms였다. **목표(p99 100ms)에 미치지 못한다.**

## 결론

- 커밋된 주문의 유실은 없었고, 복구가 평소와 같은 경로를 타므로 별도 조치 없이 이어서 처리됐다.
- 같은 시간에 매칭은 접수를 따라가지 못했다(미처리 144~206건). 3개 계좌에 주문이 몰려 접수와 체결 반영이 같은 계좌 행의 잠금을 기다린 것으로 **추정하며 아직 확인하지 않았다.** 계좌 수를 늘린 조건과 비교하고, 커넥션 풀 대기와 커밋 시간을 나눠 측정해야 한다. → [원인 측정](2026-11-24-order-latency-cause.md)에서 주원인이 디스크 동기화임을 확인했다.
