# 감사 로그 변조와 자기 승인 공격 재현

## 목적

앱 계정, 운영자, DB 관리자가 각각 기록을 고치려 할 때 막히거나 드러나는지 확인한다.

## 환경·방법

- 로컬에서 실제 core, 엔진, PostgreSQL 17, Kafka를 띄우고 체험용 사용자로 API를 호출했다. DB와 Kafka는 메모리에 두었다.
- DB 관리자 공격은 `SET session_replication_role = replica`로 트리거와 외래키를 끄고 실행했다.
- 자동 재현: `AuditChainTest`, `DatabaseRoleTest`, `AdjustmentTest`

## 결과

| 공격 | 결과 |
|---|---|
| 앱 계정으로 원장 수정, 역할 변경, 트리거 끄기 | `permission denied` |
| 소유자 계정으로 감사 로그 수정 | 트리거가 거부 |
| 관리자가 트리거를 끄고 감사 로그 1건 수정 | 검증에서 해당 로그 번호를 지목. 되돌리면 정상 |
| 파일에 남긴 뒤 체인과 로그의 뒤쪽 3건 삭제 | 체인 번호는 이어지지만 DB 밖의 값과 달라 탐지 |
| 요청자, 고객이 정정 승인 | 403, 감사 로그에 기록 |
| 같은 정정을 두 번 승인 | 409, 반대 전표는 1건 |

정정 뒤 불변식 위반은 0건이었다.

## 결론

- 역할, 앱 계정 권한, 트리거, 체인이 서로 다른 공격자를 막는다. 앞 단계가 뚫려도 다음 단계에서 드러난다.
- 한계: 앱 서버와 DB를 모두 장악한 공격은 다루지 않았다. 체인에 들어가기 전 1초, 파일에 남기기 전 1분의 틈은 남는다.
