# 묶음 커밋 적용 후 부하 중 강제 종료

## 목적

[묶음 커밋](../trade-offs/2026-11-24-batch-settlement.md)은 명령을 최대 20개씩 한 트랜잭션으로 반영한다. 묶음을 처리하던 프로세스가 죽어도 유실이나 중복 없이 이어서 처리되는지 다시 확인한다. 이전 결과는 [묶음 커밋 전 실험](2026-11-24-kill-under-load.md)에 있다.

## 환경·방법

- 커밋 `4a21eca`, 실행 jar(힙 384MB·CPU 2개·낮은 우선순위), 별도 DB. PC와 HDD는 이전과 같다.
- 체험용 계좌 3개에서 24개 동시 요청으로 주문과 취소를 보내고, 5~7초 뒤 `taskkill /f`로 종료한다. 3회 반복한다.
- 재현: `EXCHANGE_DEMO_PASSWORD=... node docs/experiments/order-load.mjs http://localhost:8081 60 accepted.txt`

## 결과

| 회차 | 접수 응답 | DB에 없는 주문 | 중복 멱등키 | 종료 직후 미처리 주문 / 취소 | 위반 (종료 직후 / 재시작 후) | 기동 / 모두 처리 |
|---|---:|---:|---:|---:|---:|---:|
| 1 | 198 | 0 | 0 | 66 / 7 | 0 / 0 | 6.5초 / 8.5초 |
| 2 | 245 | 0 | 0 | 92 / 5 | 0 / 0 | 6.5초 / 8.5초 |
| 3 | 266 | 0 | 0 | 66 / 6 | 0 / 0 | 버림 |

- 한 트랜잭션이 바꾼 주문은 최대 20~21건이었다. 묶음이 실제로 쓰였다(상대 주문이 함께 바뀌면 20건을 넘을 수 있다).
- 정지된 종목은 없었다.
- 3회차의 복구 시간은 모두 처리(6.25초)가 기동(6.52초)보다 짧게 나와 버렸다. 측정에 쓴 WSL 시계가 중간에 보정된 것으로 보인다. 1·2회차도 같은 시계라 대략적인 값이다.
- DB의 주문이 접수 응답보다 회차당 2~3건 많다. 커밋했지만 응답을 보내기 전에 죽은 요청이며, 같은 멱등키로 다시 보내면 기존 주문을 돌려준다.

## 결론

- 묶음 커밋 후에도 접수 응답한 709건 중 유실 0건, 불변식 위반 0건이다.
- 종료 직후 미처리 주문은 이전 실험(144~206건)보다 적다(66~92건). 매칭이 빨라져 덜 밀렸다. 실행 방식이 달라 정확한 비교는 아니다.
- 복구 시간(1·2회차 8.5초)은 jar로 실행해 이전(Gradle 기동 포함 16~20초)과 직접 비교할 수 없다. 목표(30초) 안이다.
- 한계: 프로세스 종료만 다뤘다. DB 종료, 디스크 손실, 네트워크 단절은 확인하지 않았다. 묶음 반영 중 정확히 어느 지점에서 죽었는지는 통제하지 않았다.
