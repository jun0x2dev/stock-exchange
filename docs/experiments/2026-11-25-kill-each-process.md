# 엔진 분리 후 프로세스별 강제 종료

## 목적

core, 매칭 엔진, Kafka, PostgreSQL이 각각 갑자기 죽어도 접수 응답한 주문이 유실되거나 두 번 처리되지 않는지 확인한다.

## 환경·방법

- Windows 11, Docker Desktop(WSL2)의 PostgreSQL 17·Kafka 4.2.2(브로커 1개, 메모리 512MB), core(힙 384MB)와 엔진(힙 128MB)은 별도 JVM. DB와 Kafka 데이터는 HDD에 있다.
- 체험용 계좌 3개에서 24개 동시 요청으로 주문과 취소를 보내다가 5초 뒤 한 프로세스를 강제 종료한다(`taskkill /f`, `docker kill`). 3초 뒤 다시 띄우고 밀린 명령이 모두 처리될 때까지 기다린다. core는 부하가 끊긴 뒤 다시 띄운다.
- 시간은 단조 증가하는 `/proc/uptime`으로 잰다.

- 순번 빈틈은 종목의 마지막 순번과 (접수 + 체결 + 취소) 건수를 비교한 것이다.
- 엔진과 Kafka가 죽은 동안에도 주문 접수는 계속됐고, 복구 뒤 모두 처리됐다. 이 구간의 시간에는 남은 부하가 끝나는 시간이 포함된다.
- 부하가 없을 때 접수→호가창 반영은 약 60ms다(엔진 분리 전 약 45ms, 같은 방법으로 12회씩).

## 결론

- 접수 응답한 3,342건 중 유실 0건, 불변식 위반 0건, 중복 체결 0건이다.
- core가 늦게 복구된 원인은 죽은 멤버가 소비자 그룹에서 만료되기를(기본 45초) 기다린 것이었다. `group.instance.id`를 고정하고 세션 만료를 10초로 줄여 목표(30초) 안으로 들어왔다.
- 한계: 프로세스 종료만 다뤘다. 전원이 나가 Kafka가 디스크에 쓰지 못한 기록을 잃는 경우는 실험하지 않았고, 통합 테스트로 멈추는 것만 확인했다. 조건마다 1~2회다.
